# 로컬 플레이어와 수동 랭킹 기록

## 진행 상태

- STEP 0: 기존 React 메뉴 / Phaser 게임 / RunSystem 분석 완료.
- STEP 1~3: 최초 닉네임, `antarctic-player` 저장, 같은 ID를 유지하는 이름 변경 완료.
- STEP 4~6: 판별 UUID, 게임오버 기록 UI, 명시적 저장과 상태 전환/중복 클릭 방지 완료.
- STEP 7: 사용자가 SQL 실행과 환경변수 설정을 완료했다. 서버용 Secret key와 실제 테이블/뷰 연결 확인 완료.
- STEP 8~11: 서버 전용 Supabase 클라이언트, POST `/api/records`, GET `/api/rankings`, 검증/중복 저장/Top 100 밖의 내 순위 연결.
- STEP 12~27: 시안에 맞춘 Ranking Board, 왕관/YOU 표시, 내 최고 SCORE/순위, 메뉴/게임오버 진입, 이름 변경, 키보드/반응형 및 로딩/빈 결과/오류 화면 구현.
- STEP 28: 자동 테스트 및 실제 DB·브라우저 검증 결과는 아래에 기록한다.

저장 버튼을 눌렀을 때만 Next.js API를 통해 실제 Supabase에 기록을 보낸다. 기존 브라우저 최고 거리/평균 기록은 유지하고 온라인 기록만 수동 저장한다. 랭킹을 열고 ESC로 돌아오면 게임오버 결과/저장 상태가 유지되고, 랭킹에서 다시 도전하면 새 판이 시작된다.

## 기존 데이터와의 연결

| 기록 | 원본 / 의미 |
| --- | --- |
| `playerId`, `nickname` | `LocalPlayerStore`, localStorage `antarctic-player` |
| `runId` | `RunSystem` 생성/재시작 때 UUID 생성, 게임오버까지 동일 |
| `score` | `round(distance × averageSpeed / 14)` |
| `distance` | `floor(distanceTravelled / unitsPerMeter)`, 정수 미터 |
| `stage` | 완료한 랜드마크 수 + 1 (현재 1~11) |
| `playTime` | 실제 주행 시간 `floor(elapsedSeconds)`, 일시정지/도착 축하 제외 |

`ScoreSystem`의 계산 함수가 전진 거리와 반올림 전 시간 가중 평균 속도로 점수를 정한다. 같은 1km라도 평균 14/28/42m/s이면 1,000/2,000/3,000점이다. 전진 거리·평균 속도에 비례하고 속도 상한이나 임의의 점수 상한을 추가하지 않는다. 평균은 실제 전진 거리 / 활성 시간이며 일시정지·축하 시간은 제외한다. 최종 선택 속도나 정수화한 playTime으로 평균을 다시 계산하지 않는다. 감속하면 전체 평균이 내려가 예상 점수가 낮아질 수 있으므로 진행 중 HUD에는 **예상 SCORE**, 게임오버에는 확정 SCORE를 표시한다.

거리 저장 단위는 미터를 유지하고 HUD/결과 화면에서만 한 번 `/ 1000`으로 변환해 소수 세 자리 km로 통일한다. 결과 문구는 “평균 … m/s로 … km 전진”이다. 기존 로컬 최고 기록은 거리 기준이므로 “최장 거리”라고 구분한다. STAGE는 완료한 랜드마크 수 + 1이며 속도·장애물·난이도를 변경하지 않는다. 랜드마크 축하가 끝나야 완료 수가 올라간다.

## 구현 경계

- `LocalPlayerStore`: 지연된 저장소 접근, trim/NFC와 Unicode 2~12자 검증, 손상/차단 저장소 처리. 유효한 기존 ID에 닉네임만 손상되면 ID를 복구해 유지한다. 저장이 차단되면 현재 세션에서만 유지된다.
- `NicknameDialog`: 최초 입력 전 플레이 불가, 기존 BGM 선택 이후 표시, 메뉴에서 변경 가능. 서버 렌더링 시 UUID/저장소에 접근하지 않는다.
- `RunSystem` / `LandmarkSystem`: 원래 게임 상태에서 기록 스냅샷만 추가.
- `GameOverPanel` / `ManualRecordSave`: 게임오버의 불변 payload, 클릭만 저장 시도, `idle → saving → saved/error`, 실패 시 동일 runId로 재시도. 새 판은 새 컨트롤러를 가져 이전 응답과 분리된다.
- `submitGameRecord`는 POST `/api/records`를 호출하며 성공 응답을 확인해야만 saved 상태가 된다. 저장 중 랭킹 진입은 잠가 완료 직전의 오래된 목록 조회를 방지한다. 클라이언트 클릭 잠금과 DB `run_id UNIQUE`를 함께 사용한다.
- `RankingStore`는 화면 진입/재시도 때만 조회하며 이전 요청 취소/응답 역전을 처리한다. 랭킹 진입 자체는 기록을 저장하지 않는다.
- `src/server/supabase.ts`는 `server-only` 경계 안에서만 키를 읽고, 세션 저장/갱신 없이 서버 클라이언트를 생성한다. SDK 2.116은 Node.js 22 이상이 필요하다.

## API와 랭킹 기준

브라우저 → Next.js Route Handler → 서버용 키 → Supabase만 허용한다. 로그인/players 테이블은 추가하지 않는다. 저장하지 않은 판은 온라인 랭킹에 들어가지 않는다. 닉네임을 바꿔도 과거 행은 수정하지 않고 최고 기록 행의 이름을 랭킹에 표시한다.

POST는 UUID, NFC/trim 닉네임 2~12자, 음수 없는 정수, 현재 STAGE 1~11, PostgreSQL integer 저장 범위를 검사한다. 요청 본문은 4KB 이하 JSON으로 제한하고 다른 Origin의 POST를 거절한다. 동일 runId/동일 payload는 `alreadySaved: true`로 성공 처리하고, 다른 payload로 재사용하면 409를 반환한다. 서버 키와 DB 오류 원문은 응답에 포함하지 않는다. 게임 점수에 상한을 추가하지는 않지만 DB의 integer 범위를 초과한 기록은 저장할 수 없다.

GET은 `leaderboard` 뷰에서 score/stage/distance DESC, created_at/player_id ASC로 상위 100명과 전체 플레이어 수를 읽는다. 본인이 100위 밖이면 해당 최고 기록보다 앞서는 행 수 + 1로 순위를 계산한다. 완전 동률도 player_id로 고정 순서를 유지한다. 목록/내 순위는 별도 조회라 동시 등록 중에는 짧은 시차가 있을 수 있다. API/SDK fetch는 no-store이고 클라이언트 조회에 15초 제한을 둔다.

로그인 없는 로컬 UUID는 인증 수단이 아니다. 현재 검증은 형식/범위/중복 방지이며 조작된 클라이언트 기록의 완전한 검증을 제공하지 않는다.

랭킹은 요청 시안의 `# / 닉네임 / SCORE / STAGE / DISTANCE`, Top 3 왕관, 내 행 YOU/라임 강조, 내 최고 SCORE/현재 순위, 메뉴/재도전/닉네임 변경으로 구성한다. 정렬은 score, stage, distance 내림차순 후 created_at 오름차순이고 완전한 동률의 최종 순서를 고정한다. 상위 100명과 별도의 내 순위를 제공한다. 빈 결과/오류/로딩 및 모바일/키보드 접근성을 검증한다.

## STEP 1~6 초기 검증 (Supabase 연결 전)

`pnpm test`의 로컬 플레이어 4개, 기록 저장 6개 테스트가 생성·재접속·이름 변경·손상/차단 저장소·Unicode 검증·runId 수명·불변 payload·명시적 저장·동시 클릭·실패 재시도·alreadySaved 응답·이전 판 응답 분리를 확인한다. 실제 DB 응답 테스트가 아닌 전송 함수 주입 테스트다.

점수 테스트 4개는 속도/거리 비례, 시간 가중 평균, 일시정지/순간 가속의 점수 부풀림 방지, 20/30/60/144 FPS 충돌 시 최종 점수 일치, 결과/저장 payload 일치, km 변환 경계를 확인한다.

2026-09-23 검증:

- 전체 테스트 107개 통과, lint/TypeScript 검사 및 `pnpm build --webpack` 통과.
- 프로덕션 브라우저: 첫 방문 BGM → 필수 닉네임, 빈 값 거절, trim, 변경/취소/재접속 복원 확인.
- 게임오버 전 자동 온라인 저장 없음, 수동 클릭 시 미연결 안내, 재도전 시 새 결과 상태 확인. 실제 저장 성공/중복 응답은 주입 테스트로만 확인했고 원격 DB 검증은 설정 후 진행한다.
- 320×360 결과 화면은 패널 높이/scrollHeight가 동일하고 버튼 접근 가능. 390×844 회전 화면 및 데스크톱 확인. 게임오버 때 패드를 숨기고 재도전 때 다시 표시하며 터치 가속이 동작한다.
- 메뉴 → 게임 → 일시정지 → 메뉴 3회 확인. 게임 캔버스 1개, 메뉴 0개. BGM 음소거 선택도 유지됐다.
- 빌드를 교체하는 중 열려 있던 검증 페이지에서 한 차례 ChunkLoadError를 확인했다. 검증 빌드를 임시 폴더에 고정하고 새 문서로 다시 연 뒤 재현되지 않았다. SQL은 아직 원격 실행/검증하지 않았다.

## STEP 7~28 최종 검증 (2026-09-23)

- 전체 자동 테스트 135개 통과. 서버 입력/본문 제한, 같은 판 동시 저장, 충돌하는 payload 거절, 빈 랭킹·Top 100·100위 밖 순위, DB 장애 응답을 포함한다. ESLint, TypeScript 및 `next build --webpack` 프로덕션 빌드 통과.
- 실제 Supabase 테이블/뷰 조회, 플레이어별 최고 기록과 SCORE → STAGE → DISTANCE → 생성 시각 정렬, 고유 run_id 제약을 임시 데이터로 검증했다.
- 프로덕션 브라우저에서 저장 전 랭킹이 비어 있음을 확인한 뒤 직접 저장해 168점/0.168km가 반영됐다. 같은 payload를 실제 API로 다시 보내면 `alreadySaved: true`이고 DB 행은 하나다. 실제 DB의 개인 순위 필터도 실행했다.
- 이름 변경 후 기존 결과/랭킹 이름은 유지된다. 랭킹의 재도전에서 새 판을 시작해 574점/0.574km를 변경된 이름으로 저장했고, 같은 playerId의 두 runId 중 최고 기록 하나만 표시되는 것을 확인했다.
- 랭킹의 ESC 복귀 시 결과/저장 완료 상태 유지, 방향키 버튼 이동과 Enter 재도전, 메뉴 복귀 시 canvas 제거를 확인했다. 새 게임 canvas는 하나다.
- 390×844 및 320×360 모바일 화면에서 표·내 기록·하단 버튼 배치를 확인했다. 320×360에서는 문서와 다이얼로그의 scroll 크기가 화면 크기와 같아 외부 스크롤이 없다.
- 브라우저 검증에서 발견한 native fetch의 잘못된 `this` 바인딩과 Next 내부 URL 정규화에 의한 정상 POST의 403을 수정하고 회귀 테스트를 추가했다.
- 검증용 DB 기록은 검증이 끝난 뒤 해당 runId만 지정해 제거했다. 실제 로그인/부정 기록 판별, 실물 게임패드 검증은 이번 랭킹 구현 범위에 포함하지 않는다.
